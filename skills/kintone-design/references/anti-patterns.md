# kintone アンチパターン集

実例ベースのアンチパターンと、そのリファクタリング案。

---

## AP-1: 集計アプリを「CQRS Read Model」と呼ぶ

### シナリオ
> 「案件管理アプリと案件収支アプリを分けました。CQRS の Read Model パターンです」

### なぜ悪い
- Fowler の CQRS 定義を満たさない（用語の濫用）
- チーム内で CQRS を正しく知っている人が混乱する
- 新メンバーに誤った学習を押し付ける

### リファクタ
- 「**Materialized View** として設計しました」
- 「kintone の関連レコードが集計できない制約への対応として、派生データを別アプリに持っています」

### 判断フロー
```
派生データを別アプリに持たせたい
  ↓
① Fowler/Greg Young の CQRS/ES 定義を満たす?
  （Command/Query 分離・Event 一次ストア・Replay 可能）
  YES → CQRS/ES と呼んで OK
  NO  → Materialized View / Data Mart と呼ぶ
```

## AP-2: 活動履歴アプリを「Event Store」と呼ぶ

### シナリオ
> 「活動履歴アプリをイベントソーシングとして扱えば、過去の状態を再構築できます」

### なぜ悪い
- kintone はレコードを直接更新できるため、ES の「全状態変更がイベント由来」を満たさない
- Kurrent（Event Store 開発元）が明確に Audit Log と ES を区別している
- 「歴史書」と「事実」を混同させる

### リファクタ
- 「**Audit Log** として設計しました」
- 「監査要件のための変更記録です」

### 正しい ES 要件（満たしてないことを確認する）
| 要件 | kintone | 評価 |
|------|---------|------|
| 全状態変更がイベント由来 | レコード直接更新可能 | ❌ |
| イベントから状態再構築 | 現在値は独立保存 | ❌ |
| Temporal Query | 任意時点の復元不可 | ❌ |
| 訂正可能なイベント列 | 履歴訂正は想定外 | ❌ |

## AP-3: Case アプリ内で関連レコード集計

### シナリオ
> 「Case アプリの計算フィールドに `SUM(外注費.金額)` と書きたい」

### なぜ悪い
- kintone の関連レコードは**標準機能で集計不可**（cybozu developer network 公式明記）
- プラグイン必須になる（アディエム等、月額コスト）
- プラグインの制約（500 件等）に将来当たる

### リファクタ
**方式 A: Materialized View（別アプリ）+ Webhook**
- CostInvoice / WorkLog の変更で案件収支アプリを更新
- Case からは粗利・利益率をルックアップ

**方式 B: 別アプリ + 日次バッチ**
- cron で全案件を走査、集計してupsert
- Phase 1 推奨（実装単純）

詳細は `physical-checklist.md` Check 4 参照。

## AP-4: サブテーブル 500 行超

### シナリオ
> 「案件のタスクリストをサブテーブルに 600 行入れている」

### なぜ悪い
- 編集画面の表示に数分〜数十分かかる（R3 Institute 実測）
- 他アプリから参照できない（集計不可）
- 外部連携ツール（Zapier 等）が扱えない
- REST API での操作が複雑

### リファクタ
- サブテーブル → **別アプリ + 関連レコード**
- マイグレーション: JS スクリプトでサブテーブルを読み取り、新アプリにレコード作成

### 判断基準
- 想定行数 > 100 → 警戒
- 想定行数 > 数百 → 別アプリ必須
- 集計・グラフ化・他アプリ参照が必要 → 別アプリ必須

## AP-5: 商品マスタ 3 個並立

### シナリオ（Cybozu 公式ガバナンス事例）
> 「営業スペースに商品マスタ、経理スペースに商品マスタ、在庫スペースに商品マスタ。それぞれ違うデータが入っている」

### なぜ悪い
- マスタ重複は**データ整合性の敵**
- どの商品マスタが「正」か不明
- 入力ミス・ズレが発生
- Cybozu 公式が「ノーコード地獄」として警告

### リファクタ
**マスタ単一化の原則**:
1. 商品マスタは**社内で 1 つ**に統合
2. 管理オーナーを明確化（例: 経理部が管理）
3. 他スペースからはルックアップで参照
4. 重複登録はカスタマイズ JS で防ぐ（重複チェック）

### ガバナンスの 4 原則
1. **命名規則**: マスタアプリには `M_` プレフィックス
2. **オーナー指定**: 全アプリに管理者を明示
3. **権限管理**: マスタは管理者のみ編集
4. **アプリ棚卸し**: 四半期に 1 回、未使用アプリを整理

## AP-6: レコード番号を一意キー

### シナリオ
> 「案件 ID にはレコード番号を使えばいいじゃないですか」

### なぜ悪い
- **データ移行で非連番化**（公式警告）
- バックアップ復元・環境間コピーで整合性が壊れる
- 業務的に意味のある番号（`DD-2026-0001`）にならない

### リファクタ
- **プラグイン採番** または **JS + REST API 採番**
- プレフィックス付き業務コード（`C-00001`, `DD-2026-0001`）
- レコード番号は内部参照用にのみ残す

## AP-7: スペース越境の乱用ルックアップ

### シナリオ
> 「営業スペースの案件アプリから、経理スペースの顧客マスタをルックアップ」

### なぜ悪い
- Bounded Context の崩壊
- スペース単位の権限管理が意味をなさなくなる
- どのスペースがマスタを持つべきか不明瞭

### リファクタ
**選択肢 A: マスタスペースの導入**
- 全社共通マスタは専用「マスタスペース」に集約
- 各業務スペースはマスタスペースからルックアップ（明確な方向性）

**選択肢 B: Anti-Corruption Layer**
- スペース間でマスタを同期するアプリを中間に置く
- 各スペースはローカルコピーを持ち、変更は中間アプリ経由

**選択肢 C: 重複登録を許容**
- スペースごとに独立したマスタ
- 「同一商品」が別レコードとして存在することを許す
- 集計時にマッピングテーブルで寄せる

## AP-8: 「DDD やります」と言ってフィールド設定だけで終わる

### シナリオ
> 「DDD の勉強してきたので、kintone で DDD 実践します！（フィールドをいろいろ追加）」

### なぜ悪い
- Aggregate 境界・不変条件・Bounded Context を設計していない
- 物理から入ると DDD ではない（それは単なるデータモデリング）
- DDD の本質（ユビキタス言語・業務モデル）が欠落

### リファクタ
**正しい順序**:
1. ユビキタス言語の抽出（`domain-model` スキル）
2. Bounded Context 特定
3. Aggregate 境界設計（Small Aggregates 原則）
4. **それから** kintone アプリへのマッピング
5. 物理設計チェックリスト（本スキル Check 1-5）
6. カスタマイズ方針決定

## AP-9: ルックアップを「リアルタイム同期」と誤解

### シナリオ
> 「顧客マスタの住所を変更したら、全ての案件に自動で反映されますよね？」

### なぜ悪い
- kintone のルックアップは**Snapshot 参照**（参照時点の値をコピー）
- マスタ変更は既存の参照レコードに自動反映されない
- バグとして発覚するケースが多い

### リファクタ
**選択肢 A: 関連レコードを使う**
- マスタ変更が自動反映される
- ただし集計不可

**選択肢 B: ルックアップ（Snapshot）を意図的に採用**
- 「契約時点の住所」を保持したい場合はこちらが正しい
- 業務ルール上の意図を明確化

**選択肢 C: 定期バッチで同期**
- ルックアップの値をマスタから再取得するバッチ
- 「最新」と「履歴」を使い分ける運用

### 決定のヒント
- 契約書・領収書に印字する情報 → Snapshot（ルックアップ）
- 現在の連絡先・担当者 → Live（関連レコード or 定期同期）

## AP-10: アプリ爆発（ノーコード地獄）

### シナリオ（Cybozu 公式事例）
> 「レコード 0 件のアプリが 71 個ある」

### なぜ悪い
- PoC で作った使い捨てアプリが放置される
- 誰も管理していないアプリが増える
- 本番アプリと実験アプリが混在

### リファクタ
**ガバナンスの仕組み**:
1. **ライフサイクル管理**: PoC / 検証 / 本番の 3 段階を明示
2. **オーナーシップ**: 全アプリに責任者を割り当て
3. **棚卸し**: 四半期ごとに「使っていないアプリ」をリストアップ
4. **命名規則**: `[業務]_[種別]_[名前]` で分類可能に
5. **削除 SOP**: 削除前のバックアップ・アクセス履歴確認

## まとめ: アンチパターン早見表

| 症状 | アンチパターン | 解決 |
|------|------------|------|
| 「CQRS っぽく」と言う | AP-1 | Materialized View と呼ぶ |
| 「Event Store」と言う | AP-2 | Audit Log と呼ぶ |
| Case で関連レコード集計 | AP-3 | 別アプリ + バッチ |
| サブテーブル 100 行超 | AP-4 | 別アプリ化 |
| マスタ重複 | AP-5 | マスタ単一化 + ガバナンス |
| レコード番号で参照 | AP-6 | JS/プラグイン採番 |
| スペース越境ルックアップ乱用 | AP-7 | マスタスペース or ACL |
| 物理先行の「DDD」 | AP-8 | ドメインモデリング先行 |
| マスタ変更が反映されない | AP-9 | 意図を選ぶ（Snapshot or Live） |
| アプリ爆発 | AP-10 | ガバナンス（命名・オーナー・棚卸し） |
