# Domain Model — 対話的ドメインモデル作成

システム要件・要望を入力として、ユースケースレベルで深掘りし、ドメインモデルを段階的に構築する。

このスキルの哲学的基盤は2つある:

1. **ドメイン＝目的**（ミノ駆動）— モデルは目的達成に特化した仕組み。良いモデルとは「問題解決ができるモデル」であり、技術的優劣ではなく目的達成能力で評価する。
2. **言語ゲーム**（ウィトゲンシュタイン）— 言葉の意味はその使用文脈で決まる。同じ「商品」でも購買者・配送者・在庫管理者で意味が違う。目的は人（アクター）が決め、言葉の意味が変わればルールも変わる。

AIの役割は「壁打ち・構造化支援」であり、ドメインの戦略判断はユーザーに委ねる。各フェーズでユーザーと対話しながら進める。

## Phase 1: 目的・アクター特定（言語ゲームの発見）

要件を読み、以下を特定する。

### 1.1 システムの目的を明確化

「何のために、誰のために存在するシステムか」を問う。曖昧なら AskUserQuestion で確認する。

```
このシステムは [誰] が [何の目的] を達成するための手段である
```

### 1.2 アクターの洗い出し

アクター＝言語ゲームのプレイヤー。各アクターは異なる目的を持ち、同じ言葉に異なる意味を与える。

各アクターについて以下を整理:
- **誰か**: 役割名
- **目的**: そのシステムで何を達成したいか
- **関心事**: 何を見たいか、何を操作したいか

### 1.3 言語ゲームの検出

同じ言葉が異なるアクター間で異なる意味を持つ箇所を探す。これが Bounded Context の境界のヒントになる。

出力フォーマット:

```markdown
## 言語ゲームマップ

| 用語 | アクターA での意味 | アクターB での意味 | 境界の示唆 |
|------|-------------------|-------------------|-----------|
| 商品 | 購入対象（価格・レビュー） | 配送対象（重量・サイズ） | 購買 vs 物流 |
```

AskUserQuestion で以下を確認:
- 特定したアクターと目的に漏れがないか
- 言語ゲームマップの解釈が正しいか

## Phase 2: ユースケース深掘り（Event Storming 的アプローチ）

各アクターの目的に沿って、業務の流れを構造化する。Event Storming の手法を対話に適用し、以下の順序で洗い出す。

### 2.1 ドメインイベントの列挙

「このシステムで何が起きるか」を過去形で列挙する。

```
- 注文が作成された
- 支払いが完了した
- 商品が発送された
```

### 2.2 コマンドの特定

各イベントを引き起こすアクション（誰が、何をするか）を紐づける。

```
| コマンド | 実行者 | 結果イベント |
|---------|--------|------------|
| 注文を作成する | 購入者 | 注文が作成された |
```

### 2.3 ポリシー・ビジネスルールの発見

イベント間の因果関係やビジネスルールを特定する。「Xが起きたら、Yする」というパターンを探す。

```
- [ポリシー] 支払いが完了したら → 在庫を引き当てる
- [ルール] 在庫が0なら → 注文を受け付けない
```

### 2.4 ユースケース整理

イベント・コマンド・ポリシーをアクター×目的の軸でユースケースに整理する。

AskUserQuestion で確認:
- 洗い出したイベント・コマンドに漏れがないか
- ポリシーやルールの解釈が正しいか
- 優先度の高いユースケースはどれか

## Phase 3: Bounded Context & ユビキタス言語

### 3.1 Bounded Context の特定

Phase 1 の言語ゲームマップと Phase 2 のユースケースから、Bounded Context の境界を引く。

判断基準:
- 同じ用語が異なる意味で使われる → 別の Context
- 同じアクターが同じ目的で使う用語群 → 同じ Context
- 独立して変更・デプロイしたい単位 → 別の Context

### 3.2 ドメイン分類

各 Bounded Context を分類する:

| 分類 | 基準 | DDD適用度 |
|------|------|----------|
| コアドメイン | 競争優位性の源泉。ここで差別化する | 厳格にDDDを適用 |
| サポートドメイン | コアを支える。自社固有だが差別化ではない | 必要に応じてDDD |
| 汎用ドメイン | どの会社でも同じ（認証、通知等） | CRUD/既存サービスで十分 |

### 3.3 ユビキタス言語辞書

各 Bounded Context 内で使う用語を定義する。Context 外では別の言葉になりうることを明示する。

```markdown
## [Context名] のユビキタス言語

| 用語 | 定義 | 他Contextでの対応概念 |
|------|------|---------------------|
| 注文 | 購入者が商品を購入する意思表示 | 物流Contextでは「出荷依頼」 |
```

### 3.4 Context Map

Bounded Context 間の関係を定義する。

関係パターン:
- **Shared Kernel**: 共有する小さなモデル
- **Customer-Supplier**: 上流が下流のニーズに応える
- **Conformist**: 下流が上流のモデルに従う
- **Anti-Corruption Layer**: 変換層を挟んで独立性を保つ
- **Published Language**: 公開されたインターフェース

AskUserQuestion で確認:
- Context の切り方が妥当か
- ドメイン分類（コア/サポート/汎用）が正しいか

## Phase 4: 戦術設計（Aggregate / Entity / Value Object）

コアドメインとサポートドメイン（DDD適用対象）の各 Bounded Context について、戦術的パターンを適用する。

### 4.1 Aggregate の特定

Vaughn Vernon の4ルールに従う:

1. **真の不変条件を整合性境界でモデリングせよ** — トランザクション整合性が必要なオブジェクト群で Aggregate 境界を決める
2. **小さな Aggregate を設計せよ** — Root Entity と最小限の属性・Value Object に限定
3. **他の Aggregate は ID で参照せよ** — 直接のオブジェクト参照ではなく ID による間接参照
4. **境界外では結果整合性を使え** — Aggregate 間はドメインイベントによる結果整合性

### 4.2 Entity と Value Object の判別

| 判断軸 | Entity | Value Object |
|--------|--------|-------------|
| 同一性 | ID で識別。状態が変わっても同じもの | 属性の等価性で比較 |
| 可変性 | ライフサイクルを持ち状態変化する | 不変（イミュータブル）。変更＝新しいインスタンス作成 |
| 例 | ユーザー、注文 | 金額、住所、期間 |

同じ概念でも Context によって変わりうる（例: 住所は EC では Value Object、電力会社では Entity）。

### 4.3 不変条件の導出（データ破壊駆動）

ミノ駆動のデータ破壊駆動アプローチで、各モデルの制約を導出する。「このデータをどう壊せるか？」と問い、壊れ方から守り方を逆算する。

各 Aggregate / Entity / Value Object について:

```markdown
### [モデル名] の不変条件

#### 破壊シナリオ
- 金額に負の値を設定できたら？ → 不正な請求が発生
- 注文ステータスを「発送済み」から「未払い」に戻せたら？ → 業務フローが破綻

#### 導出された不変条件（安定 ID 付与）
- **I-1** 金額は 0 以上であること
- **I-2** ステータス遷移は [未払い → 支払済 → 発送済 → 完了] の一方向のみ

#### 実装方針
- コンストラクタで検証
- 不変フィールド（イミュータブル）
- 状態遷移メソッドでガード
```

**安定 ID の付与理由**: 不変条件には Aggregate ローカルの安定 ID（`I-1, I-2 ...`）を付与する。Properties 表の Description や状態遷移図、テスト設計から不変条件を参照するときにトレーサビリティが確保できる。内部 Entity 固有の不変条件は `OI-1` のような Entity 固有 prefix で区別する（OrderItem なら `OI-`）。

#### Corrective Policy（結果整合で扱う制約）

全ての制約を Aggregate の即時整合（トランザクション内）で守る必要はない。「即時に守ると Aggregate が肥大化する」「他 Aggregate の状態に依存する」場合は、結果整合で扱う **Corrective Policy** として切り分ける。

```
- [CP-1] 在庫チェックは結果整合 → 失敗時は OrderHeldForBackorder を発行（即時ロールバックしない）
```

不変条件 vs Corrective Policy の判断基準:

- **不変条件 (I-N)**: Aggregate 自身が即時に守るべき。違反したらコンストラクタ・メソッドで拒否
- **Corrective Policy (CP-N)**: 結果整合で扱う。違反検知後は補正アクション（補償イベント等）で対応

### 4.4 リッチドメインモデルの確認

貧血ドメインモデル（データだけ持ってロジックがない）を避ける。各 Entity / Aggregate Root が以下を満たすか確認:

- ビジネスルールをメソッドとして持つか
- 不変条件を自身で守れるか
- 外部のサービスクラスにロジックが漏れていないか

ただし、単純な CRUD のサブドメインでは貧血モデルで十分。無理にリッチにしない。

AskUserQuestion で確認:
- Aggregate の粒度が適切か
- 不変条件に漏れがないか
- Entity / Value Object の判別が妥当か

## Phase 5: ドメインモデル出力

全フェーズの成果を統合し、構造化されたドメインモデルを出力する。

### 適用度の段階的厳格さ（重要）

DDD の主流見解（Vernon, Evans, ddd-crew）は「**コアドメインに DDD を集中、汎用ドメインは CRUD で十分**」。Phase 3.2 で分類した3区分ごとに出力厳格さを段階適用する：

| 分類 | 必須セクション | 省略可セクション |
|------|--------------|----------------|
| **コアドメイン** | Description / Structure / Properties / Domain Events / Invariants / Corrective Policies / State Transitions の **全7セクション省略禁止** | なし |
| **サポートドメイン** | Description / Properties / Domain Events / Invariants（最低限） | Structure / Corrective Policies / State Transitions（持つ場合「なし」明示。CRUD なら省略可） |
| **汎用ドメイン** | Description / Properties / Domain Events の **3セクション最小** | Structure / Invariants / Corrective Policies / State Transitions（**全て省略可**。汎用に DDD 戦術設計を強制しない） |

「省略可」は **必要があれば書いてもよい**意味。汎用ドメインを無理にリッチドメインモデル化しないこと。

### 出力構造のサマリ

```
# ドメインモデル: [システム名]
## 概要
## Context Map
## ユビキタス言語辞書
---
## Bounded Context: [Context名]（分類: コア/サポート/汎用、責務: ...）
### [Aggregate名] (Aggregate Root)
  **Description**, [Structure], Properties, Domain Events, [Invariants], [Corrective Policies], [State Transitions]
  #### [内部Entity名] (Entity, internal to ...)
### Value Objects ([Aggregate名] scope)
---
## Cross-Aggregate Reference Map（Aggregate ≥2 のみ。Mermaid erDiagram）
```

### 詳細フォーマット

**最終出力を生成する直前に必ず `references/output-format.md` を読むこと**。そこには以下が含まれる：

- 出力テンプレート（コアドメイン用フル形式）
- サブドメイン別の最小構成（サポート / 汎用用）
- フォーマット細部ルール（Properties 表 / Domain Events 表 / Invariants / Corrective Policies / State Transitions / Structure / Aggregate Root vs Entity vs VO / Cross-Aggregate Reference Map）
- 詳細な自己評価チェックリスト（戦略設計 / 分類別 / フォーマット規約 / 全体構造）

### 簡略チェック（出力直前）

最終確認は references/output-format.md の詳細チェックリストで行うこと。SKILL.md レベルでは以下の最重要項目だけ確認：

- [ ] 各 Bounded Context にコア/サポート/汎用の分類が付与されているか
- [ ] 分類に応じた適切な詳細度で出力されているか（コアは全7セクション、汎用は3セクション最小）
- [ ] 不変条件に安定 ID（I-N）が付与されているか（コア・サポート）
- [ ] Aggregate 間は ID 参照のみか（Vernon ルール3）
- [ ] 貧血モデル化していないか（**コア・サポートのみ**該当。汎用は CRUD で OK）
- [ ] Aggregate が 2 つ以上の場合、Cross-Aggregate Reference Map が Mermaid `erDiagram` で出力されているか

## 進め方のガイドライン

- **対話的に進める**: 各フェーズの終了時に AskUserQuestion でユーザーの確認を取る。一気に全フェーズを駆け抜けない
- **仮説を立ててから聞く**: 「Xだと思いますが合っていますか？」の形式で問う。白紙から聞かない
- **段階的に詳細化**: Phase 1-2 は広く浅く、Phase 3-4 で深く。最初から完璧を目指さない
- **適材適所**: 全てのドメインに DDD を適用しない。コアドメインに集中する
- **出力は構造化**: 最終出力は上記フォーマットに従い、後続の設計工程（データ設計等）に引き継げる形にする
