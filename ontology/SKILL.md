# Ontology — コードベース知識グラフの構築と継続更新

フォルダ名やタグは「何という名前か」しか伝えない。オントロジーは「order-service は payment-service を `calls` する」という**関係そのものを型として確定**させる。以降のセッションはコードを広く読み直す代わりにグラフを参照すればよくなり、探索トークンと応答時間が大きく減る（元記事の実測: キャッシュ読取トークン 84% 減、応答 3 倍速）。

このスキルの成果物は 2 つ:

1. `.claude/ontology/` — git 管理されるグラフ本体(README.md / entities.yaml / relations.yaml / constraints.md)
2. **CLAUDE.md への注入セクション** — 「構造変更をしたら同セッション内でオントロジーも更新する」ルール。これが「今後も作成され続ける」を担保する心臓部なので、Bootstrap では省略しないこと

ファイル書式・関係語彙・記入例は `references/format.md` に正本がある。**ファイルを生成する前に必ず読むこと。**

## モード判定

- `.claude/ontology/` が存在しない → **Bootstrap**
- 存在する → **Update**（「作り直して」と明示されたら Bootstrap をやり直してよい）

## Bootstrap

### 1. 規模の見立て

ソースファイル数を概算する（`git ls-files | grep -cE '\.(ts|js|py|go|rb|java|rs|...)$'` など）。30 ファイル未満の小規模プロジェクトではオントロジーはノイズになりやすい。その場合も作成はするが、エンティティ数を一桁に抑えた最小構成にし、完了報告で「小規模なので効果は限定的」と正直に伝える。

### 2. コードベース探索

エントリポイント、モジュール境界、ビルド/依存設定（package.json, go.mod, pyproject.toml など）、README・ADR・docs を読む。数百ファイル超の場合は Explore サブエージェントを領域ごとに並行で出し、各領域の「主要コンポーネントと依存・呼び出し関係」の要約だけを受け取る。

### 3. エンティティ抽出 — 粒度が命

粒度は**モジュール / サービス / ドメイン概念 / データストア / 外部システム**のレベル。ファイル単位・関数単位のエンティティは作らない。オントロジーは索引であってコードの複製ではない — 全ファイル合計が 1 回のツールコールで読み切れる量（目安 300 行以内、エンティティ 10〜50 個）に収まらないなら粒度が細かすぎる。

### 4. 関係抽出 — 根拠のあるものだけ

関係型は `references/format.md` の定義済み語彙（`is-a`, `part-of`, `calls`, `depends-on`, `emits`, `consumes`, `reads-from`, `writes-to`）から選ぶ。定義済みの型から選ぶことで、あり得ない関係や曖昧な関係が混入しにくくなる。新しい型がどうしても必要な場合は、まず relations.yaml の語彙表に定義を追加してから使う。

各関係には根拠となるコード位置を `evidence` として付ける。**コードで確認できていない推測の関係は書かない。**確からしいが未確認のものは、書くより落とす方が安全 — 誤った関係は「参照すれば正しい」というオントロジーの価値そのものを壊す。

### 5. 制約抽出

README・ADR・lint 設定・一貫したコードパターンから「このアーキテクチャで守られている成立条件」を抽出し、根拠と一緒に constraints.md へ書く（例: 「サービスは他サービスの DB を直接参照しない — 根拠: docs/adr/0003」）。根拠が見つからない一般論は書かない。

### 6. ファイル生成

`references/format.md` のスキーマ通りに `.claude/ontology/` へ 4 ファイルを生成する。README.md には現在の HEAD コミットを `last_synced_commit` として記録する（Update 時のドリフト検出の起点になる）。

### 7. CLAUDE.md への注入

プロジェクトルートの CLAUDE.md に、`references/format.md` の「CLAUDE.md 注入テンプレート」セクションをマーカー付きで追記する。CLAUDE.md が無ければ新規作成する。既に `<!-- ontology:start -->` マーカーがあれば中身をテンプレートの最新版で置き換える（重複追記しない）。

CLAUDE.md は毎セッション自動ロードされるため、この注入によって以降のすべてのセッションが「構造の質問はまずオントロジーを参照」「構造変更をしたら同セッション内でオントロジーを更新」を実行するようになる。これがスキルを再発火させなくてもグラフが育ち続ける仕組み。

### 8. 完了報告

エンティティ数・関係数・制約数、CLAUDE.md への注入結果、今後の維持のされ方（どういう変更をしたときに何が更新されるか）を報告する。

## Update

### 1. ドリフト範囲の特定

README.md の `last_synced_commit` を読み、`git log --stat <commit>..HEAD` で構造に関わる変更を特定する:

- ディレクトリ・モジュールの追加/削除/改名
- 依存設定ファイル（package.json 等）の変更
- 公開 API・イベント定義・スキーマの変更

`last_synced_commit` が無い・無効な場合は直近の変更（例: 30 コミット）を対象にし、その旨を報告する。

### 2. 差分の反映

変更に対応する entities / relations / constraints を更新する。削除・改名されたエンティティは**消す**（改名は id を付け替える）。グラフの価値は鮮度にあり、履歴は git が持っているので、古いエントリを「deprecated」として残さない。

### 3. スポットチェック

差分に現れなかった既存関係からも数件サンプリングし、`evidence` のコード位置が今も実在し関係が成立しているか確認する。乖離があればコードを正としてオントロジーを直す。

### 4. 同期完了

`last_synced_commit` を現在の HEAD に更新する。CLAUDE.md のマーカーセクションが消えていたり古かったりしたら復元する。何をどう変えたか（追加/削除/修正したエンティティ・関係）を報告する。

## 品質チェックリスト

生成・更新の最後にセルフチェックする:

- [ ] relations.yaml の `from`/`to` はすべて entities.yaml に定義された id か（参照整合性）
- [ ] 使った関係型はすべて語彙表に定義があるか
- [ ] すべての関係に `evidence` があり、そのパスが実在するか
- [ ] ファイル・関数単位のエンティティが混入していないか
- [ ] 全体量は 1 回で読み切れる範囲か
- [ ] CLAUDE.md にマーカー付きセクションが 1 つだけ存在するか
